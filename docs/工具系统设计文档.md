# 智能旅行规划系统 —— 工具系统（Tool System）设计文档

> 项目：travelAgent
> 技术栈：LangChain 1.x `create_agent` + LangGraph + MCP（Model Context Protocol）+ FastMCP + PostgreSQL Store
> 文档日期：2026-09-26

---

## 一、总体架构概览

本系统的工具系统采用 **"分层 + 动态注入 + 工具即 Agent"** 的复合设计，整体分为四层：

```
┌─────────────────────────────────────────────────────────────┐
│                     主 Agent（travel_agent）                  │
│         create_agent + StepConfigMiddleware（动态配置）        │
├─────────────────────────────────────────────────────────────┤
│                      工具层 app/tools/                        │
│  ┌──────────┬──────────┬──────────┬──────────┬───────────┐  │
│  │ 状态流转  │ 状态回退  │ 长期记忆  │ RAG 检索  │ 复合查询   │  │
│  │ 8 个工具  │ 9 个工具  │ 6 个工具  │ 4 个工具  │ 2 个工具   │  │
│  └──────────┴──────────┴──────────┴──────────┴───────────┘  │
│              + MCP 工具筛选器（mcp_tools.py）                 │
├─────────────────────────────────────────────────────────────┤
│                   MCP 层 app/mcp_core/                        │
│   MCPClientManager（单例） ──┬── 自建 stdio Server（天气/搜索） │
│                             └── 外部 HTTP 服务（高德/12306/   │
│                                 航旅纵横/酒店）               │
├─────────────────────────────────────────────────────────────┤
│                   子 Agent 层 app/agents/                     │
│   handoffs（主流程） / routers（并行路由） / subagents（交通）  │
└─────────────────────────────────────────────────────────────┘
```

**核心设计思想：**

1. **工具不只是函数，而是状态机控制器** —— 工具通过 LangGraph 的 `Command` 对象直接修改图状态（`TravelState`）并驱动步骤跳转。
2. **工具按需注入，而非全量挂载** —— 中间件根据当前步骤（`current_step`）动态替换 system prompt 和可用工具集。
3. **工具即子 Agent（Tool-as-Agent）** —— 复杂查询被封装成工具，内部实际是完整的子 Agent / 子图，实现能力的多层嵌套。
4. **MCP 统一接入外部能力** —— 自建与第三方服务统一收敛到 MCP 协议，通过筛选器按需分配给不同 Agent。

## 二、六大工具体系详解

### 2.1 状态流转工具（`app/tools/state_transition.py`）—— 流程推进器

这是整个 Handoffs 多步骤流程的"前进引擎"，共 **8 个工具**，对应规划流程的 8 个步骤：

| # | 工具 | 作用 | 跳转目标 |
|---|------|------|----------|
| 1 | `record_requirement_tool` | 记录用户需求（日期/天数/预算/风格等） | `destination_recommendation` |
| 2 | `select_destination_tool` | 确认目的地 | `transport_planning` |
| 3 | `select_transport_tool` | 确认交通方式（flight/train/driving） | `accommodation_planning` |
| 4 | `select_accommodation_tool` | 确认住宿类型（可多选） | `food_planning` |
| 5 | `select_food_tool` | 确认餐饮偏好（可多选） | `itinerary_generation` |
| 6 | `generate_itinerary_tool` | 生成每日行程 | `budget_summarization` |
| 7 | `summarize_budget_tool` | 汇总预算明细 | `order_generation` |
| 8 | `generate_order_tool` | 生成订单号，流程终结 | —— |

**关键机制：Command + ToolRuntime**

每个工具都接收 LangGraph 注入的 `ToolRuntime[None, TravelState]` 参数，并返回 `Command` 对象：

```python
return Command(update={
    "messages": [ToolMessage(content="...", tool_call_id=runtime.tool_call_id)],
    "user_requirement": requirement,          # 写入业务数据
    "current_step": "destination_recommendation"  # 驱动步骤跳转
})
```

一次工具调用同时完成三件事：
1. **回写消息**：通过 `ToolMessage` 向对话历史写入执行结果（LLM 可见）；
2. **更新状态**：把业务数据（需求、选择项、行程、预算等）写入 `TravelState`；
3. **推进流程**：修改 `current_step`，下一步中间件会据此切换 prompt 和工具集。

**内置校验逻辑：**
- 日期格式校验（`YYYY-MM-DD`），失败时返回错误 `ToolMessage` 且不跳转；
- 枚举值校验（交通方式、住宿类型、餐饮类型必须在合法集合内）；
- 预算等级自动推断（人均 <3000 → economy，3000-8000 → comfort，>8000 → luxury）；
- `generate_itinerary_tool` 执行前检查 5 个前置字段是否齐全。

### 2.2 状态回退工具（`app/tools/state_back.py`）—— 流程倒车档

规划流程不是单行道。回退工具体系让用户可以随时"反悔"，共 **9 个工具**：

**① 通用回退 `go_back_to_step`**

核心参数：
- `target_step`：目标步骤（Literal 枚举，禁止回退到 `order_generation`）；
- `reason`：回退原因（记录到消息历史，便于追溯）；
- `clear_subsequent_data`：是否清除目标步骤之后的数据（默认 `True`）。

**数据清除机制**是本工具的精髓 —— 通过两张映射表实现精准清理：

```python
ALL_STEPS = ["requirement_collection", "destination_recommendation", ...]  # 步骤全序
STEP_STATE_FIELDS = {
    "transport_planning": ["selected_transport", "transport_options"],
    ...
}
```

回退时，从目标步骤开始向后遍历 `ALL_STEPS`，把每个步骤对应的状态字段置为 `None`，保证状态一致性，避免"旧数据污染新决策"。

**② 快捷回退工具（7 个）**

`go_back_to_requirement` / `go_back_to_destination` / `go_back_to_transport` / `go_back_to_accommodation` / `go_back_to_food` / `go_back_to_itinerary` / `go_back_to_budget`

它们本质上是对通用工具的**参数固化封装**（内部调用 `go_back_to_step.invoke({...})`），每个工具的 docstring 都写满了中文口语触发场景（如"不想坐飞机了"→ 回退交通），**降低 LLM 的工具选择成本**。

**③ 进度查询 `check_current_progress`**

只读工具，遍历 `ALL_STEPS` 生成"已完成/当前/待完成"的可视化进度文本，并汇总已收集的关键信息（日期、人数、目的地等）。

### 2.3 长期记忆工具（`app/tools/memory_tools.py`）—— 用户画像读写器

基于 LangGraph `AsyncPostgresStore` 的跨会话长期记忆，共 **6 个工具**：

| 工具 | 读写 | 作用 |
|------|------|------|
| `get_user_memory_tool` | 读 | 获取用户完整画像（风格/饮食/历史） |
| `update_travel_style_tool` | 写 | 旅行风格（休闲度假/文化探索/户外冒险/美食之旅） |
| `update_food_preference_tool` | 写 | 饮食口味（辣/甜/清淡/海鲜…） |
| `update_dietary_restriction_tool` | 写 | 饮食禁忌/过敏（健康相关，重点记录） |
| `update_accommodation_preference_tool` | 写 | 住宿类型偏好 + 每晚预算 |
| `add_travel_record_tool` | 写 | 历史出行记录（避免重复推荐） |

**设计要点：**

1. **user_id 从运行时状态获取**：`runtime.state.get('user_id')`，工具本身不接收 user_id 参数，防止 LLM 伪造身份；
2. **docstring 即 Few-Shot**：每个工具的文档里写满"用户说 X → 参数为 Y"的映射示例，引导 LLM 在对话中**主动、即时**地抽取并保存偏好；
3. **优雅降级**：user_id 缺失或服务异常时返回友好提示而非抛异常，不打断对话流；
4. 与中间件配合：中间件每次调用 LLM 前自动注入 `format_memory_for_prompt(user_id)` 的长期记忆摘要，工具负责"写"，中间件负责"读"，形成闭环。

### 2.4 RAG 检索工具（`app/tools/rag_tools.py`）—— 知识库门户

将 Advanced RAG 管道封装为 4 个 Agent 可自主调用的工具：

| 工具 | category 过滤 | 知识范围 |
|------|--------------|----------|
| `search_destination_guide` | `destinations` | 景点介绍、门票、行程骨架 |
| `search_food_recommendations` | `food` | 分城市美食、小吃街、人均价 |
| `search_accommodation_info` | `accommodation` | 住宿区域对比、价位、动线 |
| `search_travel_tips` | `tips` | 注意事项、季节、避坑指南 |

**设计要点：**

1. **单例懒加载管道**：`_get_rag_pipeline()` 全局只初始化一次 —— 加载语料 → `ParentDocumentSplitter` 父子文档切分 → 加载/创建 Chroma 向量库 → 构建 `AdvancedRAGPipeline`（multi_query 策略 + top_k=3 + 缓存）；
2. **category 硬过滤防污染**：四个工具共用同一管道，但通过元数据 category 强制过滤，避免"美食工具搜到住宿文档"的跨类污染；
3. **结果格式化**：每条结果截断 800 字并附带 `类型/城市/来源` 元信息，方便 LLM 判断资料可信度；
4. **错误处理**：检索异常时抛出 `ToolException`，让 LangChain 把错误信息反馈给 LLM 进行自我修正。

### 2.5 复合查询工具（工具即子 Agent / 子图）

这是本系统最有特色的设计 —— **工具内部不是简单 API 调用，而是完整的 Agent 系统**。

**① `query_destination_info`（`router_query.py`）→ 并行 Router 子图**

内部调用 `create_destination_router()` 构建的 LangGraph 子图：

```
START → classifier（LLM 结构化输出分类意图）
          ├─ Send → explore 节点（带 RAG 工具的探索 Agent）
          └─ Send → weather 节点（天气 Agent）
        → synthesizer（合并结果）→ END
```

- 分类器用 `with_structured_output(ClassificationResult)` 输出要调用的 Agent 列表；
- `route_to_agents` 返回 `Send` 对象列表，LangGraph **并行执行**多个 Agent；
- `agent_results` 使用 `Annotated[list, add]` Reducer 聚合并行结果；
- 最终报告作为字符串返回给主 Agent。

**② `query_transport_options`（`transport_query.py`）→ 三级 Agent 嵌套**

```
主 Agent（travel_agent）
  └─ 工具 query_transport_options
       └─ 交通协调器 Agent（transport_coordinator）
            ├─ 工具 query_flights  → 航班子 Agent → 航旅纵横 MCP 工具
            ├─ 工具 query_trains   → 高铁子 Agent → 12306 MCP 工具
            ├─ 工具 plan_driving_route → 自驾子 Agent → 高德地图 MCP 工具
            └─ 辅助 MCP 工具（天气/日期/周边搜索）
```

- 协调器把三个子 Agent 用 `@tool` 装饰器**包装成工具**（Tool-as-Agent 模式）；
- 每个子 Agent 持有自己筛选过的 MCP 工具集和专家级 system prompt（如航班 Agent 内置 IATA 三字码知识）；
- 协调器按距离启发式决策：<300km 推荐高铁，300-1000km 高铁/航班，>1000km 航班；
- 工具层负责把结构化参数"翻译"成自然语言查询再交给协调器，**子 Agent 只面对自然语言，接口极其简单**。

### 2.6 MCP 工具筛选器（`app/tools/mcp_tools.py`）—— 按需分配器

MCP 客户端一次性加载所有服务的工具（可能几十个），筛选器按**名称关键词**把工具分组，供不同场景按需取用：

| 函数 | 关键词 | 用途 |
|------|--------|------|
| `get_all_mcp_tools()` | 全部 | 兜底/测试 |
| `get_hotel_tools()` | `find-hotels`, `maps_around_search` | 住宿规划步骤 |
| `get_weather_tools()` | `get_weather_forecast` | 天气查询 |
| `get_search_tools()` | `search_travel_info` | 联网搜索补充 |
| `get_date_tools()` | `get-current-date`, `getTodayDate` | 相对日期→绝对日期转换 |

子 Agent 层也有各自的筛选逻辑（如航班 Agent 按 `flight/aviation/searchflights/gettodaydate` 筛选）。

## 三、MCP 层设计（`app/mcp_core/`）

### 3.1 MCPClientManager —— 统一连接管理（单例）

`client.py` 中的 `MCPClientManager` 是整个 MCP 体系的中枢：

- **单例 + asyncio.Lock 双重检查**，保证并发安全；
- 基于 `langchain_mcp_adapters.MultiServerMCPClient`，一份配置统一管理 **5 个服务**：

| 服务 | 类型 | 传输方式 | 提供能力 |
|------|------|----------|----------|
| `weather` | 自建 | stdio | 高德天气预报 |
| `search` | 自建 | stdio | Tavily 旅游搜索 |
| `amap` | 外部 | streamable_http | 高德地图（周边/路线） |
| `12306-mcp` | 外部 | streamable_http | 高铁车次查询 |
| `VariFlight-Aviation` | 外部 | streamable_http | 航班查询 |
| `aigohotel-mcp` | 外部 | streamable_http | 酒店搜索 |

- **stdio 服务自动注入 `PYTHONPATH`**，保证子进程能 import 项目模块；
- 初始化时**预加载工具列表并缓存**（`get_tools()` 懒加载 + 缓存双策略）；
- 提供 `reset_instance()` 便于测试。

### 3.2 自建 MCP Server（FastMCP）

**`weather_server.py`**：封装高德天气 API。注意其 docstring 中直接内置了常用城市的 adcode 对照表（北京=110000、西安=610100…），这是**面向 LLM 的接口设计** —— 因为 API 只认 adcode 不认中文名，所以把编码知识写进文档让 LLM 自己完成转换。

**`search_server.py`**：封装 Tavily 搜索 API，限制最多 10 条结果、内容截断 300 字，控制返回体积防止撑爆上下文。

两个 Server 都以 `python -m app.mcp_core.servers.xxx` 的 stdio 方式被主进程拉起，**进程隔离**带来稳定性（某个服务崩溃不影响主 Agent）。

## 四、动态工具注入机制（核心亮点）

### 4.1 StepConfigMiddleware（`app/core/middleware.py`）

这是把"工具系统"和"流程状态机"粘合起来的关键。它在**每次 LLM 调用前**执行：

```
LLM 请求 → 中间件拦截
   1. 读取 state['current_step']
   2. 校验 requires 前置依赖字段（不齐则抛错）
   3. 加载用户长期记忆 → 追加到 prompt 末尾
   4. 用 state 字段填充 prompt 模板占位符（{selected_destination} 等）
   5. request.override(system_prompt=..., tools=当前步骤的工具集)
→ 发给 LLM
```

### 4.2 步骤配置表（`app/agents/handoffs/step_config.py`）

`get_step_config()` 返回 8 个步骤的配置字典，每步包含：

- `prompt`：该步骤的专家级系统提示词（含对话风格、任务流程、回退场景、工具调用规则）；
- `tools`：**该步骤可见的工具子集**；
- `requires`：进入该步骤的前置状态字段。

**工具分配遵循"最小权限 + 有限回退"原则**，例如：

| 步骤 | 前进工具 | 能力工具 | 记忆工具 | 可回退到 |
|------|----------|----------|----------|----------|
| 需求收集 | record_requirement | date_tools | 风格/禁忌/口味/出行记录 | —— |
| 目的地推荐 | select_destination | query_destination_info + RAG + 搜索 | 风格/出行记录 | 需求 |
| 交通规划 | select_transport | query_transport_options | —— | 目的地、需求 |
| 住宿规划 | select_accommodation | hotel_tools + RAG | 住宿偏好 | 交通、目的地、需求 |
| 餐饮规划 | select_food | RAG | 禁忌/口味 | 住宿、交通、目的地、需求 |
| 行程生成 | generate_itinerary | RAG | —— | 餐饮、住宿、交通、目的地、需求 |
| 预算汇总 | summarize_budget | —— | —— | 全部（含通用 go_back_to_step） |
| 订单生成 | generate_order | —— | 出行记录 | 全部 |

这样做的好处：
1. **防止 LLM 跳步/乱序**：当前步骤看不到未来的工具，无法越级调用；
2. **缩小决策空间**：每次只给 LLM 5-10 个工具而非全部 30+，工具选择准确率显著提升；
3. **回退权限随流程递增**：越靠后的步骤可回退的范围越大，符合业务直觉。

## 五、状态定义（`app/core/state.py`）

`TravelState` 继承 `AgentState`（自带 `messages`），按用途分五组字段：

- **流程控制**：`current_step`（8 步 Literal 枚举）；
- **用户输入**：`user_requirement`（`UserRequirement` TypedDict，含预算等级推断结果）；
- **用户选择**：`selected_destination` / `selected_transport` / `selected_accommodation_types` / `selected_food_types`；
- **查询结果**：`destination_options` / `transport_options` / `accommodation_options` / `food_options`；
- **最终结果**：`itinerary` / `budget` / `report` / `order_id`。

所有可选字段用 `NotRequired` 标记，配合回退工具的"置 None 清理"实现状态的精确生命周期管理。

## 六、设计亮点总结

| 设计模式 | 体现位置 | 解决的问题 |
|----------|----------|-----------|
| **Command 模式** | state_transition / state_back | 工具调用 = 状态变更 + 流程跳转，三位一体 |
| **中间件动态注入** | middleware.py | 同一 Agent 在不同步骤拥有不同"人格"（prompt）和"能力"（工具） |
| **Tool-as-Agent** | transport_query / router_query | 复杂能力封装为简单工具接口，主 Agent 无感知 |
| **并行路由（Send API）** | destination_router | 探索 + 天气并行查询，降低延迟 |
| **单例 + 懒加载** | MCP 客户端 / RAG 管道 / Store | 昂贵资源只初始化一次 |
| **关键词筛选** | mcp_tools / 各子 Agent | 大工具池按需切分，控制上下文体积 |
| **docstring 工程** | 所有工具 | docstring 写满触发场景和参数示例，本质是给 LLM 的 Few-Shot 提示 |
| **最小权限原则** | step_config 工具分配 | 防止跳步，提升工具选择准确率 |
| **状态精确清理** | STEP_STATE_FIELDS 映射 | 回退不产生脏数据 |
| **身份注入而非传参** | memory_tools 的 user_id | 防止 LLM 伪造用户身份 |

## 七、一次完整调用的数据流（示例）

以"用户确认目的地为西安"为例：

```
用户: "就去西安吧"
  ↓
主 Agent（current_step=destination_recommendation）
  ↓ 中间件注入：目的地推荐 prompt + [query_destination_info, select_destination_tool, RAG×4, 搜索, 记忆×2, go_back_to_requirement]
  ↓
LLM 决策调用 select_destination_tool(destination="西安")
  ↓
工具返回 Command:
  - messages += ToolMessage("目的地已确认:西安")
  - selected_destination = "西安"
  - current_step = "transport_planning"     ← 状态机跳转
  ↓
Checkpointer 持久化状态（短期记忆）
  ↓
下一轮 LLM 调用，中间件检测到 current_step=transport_planning
  ↓ 重新注入：交通规划 prompt + [query_transport_options, select_transport_tool, 回退×2]
  ↓
LLM 以"交通规划专家"人格继续对话……
```

## 八、已知限制与改进方向
